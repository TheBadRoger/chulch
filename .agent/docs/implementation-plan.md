# mcdocker 实现方案

## 目标与边界

用户可维护多个 Minecraft Java 版整合包，分别启动、升级和删除实例。相同内容的游戏、库、加载器、模组及资源文件可以共享。存档、配置、日志、截图和玩家选项按实例保存。目录隔离只负责区分实例数据，运行中的模组仍拥有当前用户授予 Java 进程的权限。

首版交付 Windows CLI。命令覆盖导入、列出实例、配置下载源、启动、更新、回退与清理预览。Fabric、Forge 和 NeoForge 各有一组真实整合包启动用例。具体 Minecraft、Java 与加载器版本组合以验收矩阵公布。

启动器自行定义数据根，例如 `store/` 保存对象，`layers/` 保存分层清单，`instances/<id>/profile.json` 保存实例配置，`instances/<id>/game/` 保存私有游戏数据，`work/` 保存安装与运行暂存。由加载器适配器生成启动计划，向 Java、Minecraft 和加载器提供各自要求的路径。只有按相对路径发现的文件才需要在运行视图中按约定布局。

## 存储模型

| 对象 | 职责 |
| --- | --- |
| 全局对象库 | 以 SHA-256 标识文件字节，保存通过校验的原始内容 |
| 游戏层 | 引用指定版本的客户端、公共库和资源 |
| 加载器层 | 引用与游戏版本、运行平台匹配的加载器及其依赖 |
| 整合包层 | 跟踪包所需的模组和其他托管文件，可保存用于初始化实例的配置模板 |
| 实例 | 保存层引用、启动选项、私有数据和当前启用的版本 |

逻辑层按游戏、加载器、整合包的顺序解析。显式批准的覆盖才可替换同一目标路径。实例的可写配置从模板初始化一次，后续升级保留已有内容。被包移除的托管文件应从新一代运行视图消失，同时保留用户文件。加载器和常用模组分别以经解析的实际文件为共享单位，无需为每个常用模组另外拆层。

## 从导入到启动

现代客户端在安装时合并原版与加载器的启动清单，保存加载器类型、版本、Java 要求、主类、JVM 参数和游戏参数。运行时按当前实例补入路径、玩家名和存档名。旧 Fabric 实例继续使用原有离线参数。复用基础层时同时匹配 Minecraft 版本、加载器类型和加载器版本。

Forge 与 NeoForge 的在线安装共用官方安装器调用流程。使用已备妥的本地源时，直接读取安装后的版本清单。对使用 BootstrapLauncher 的客户端，还需收集它按 Maven 路径定位的运行文件，这些文件随实例启动准备，但无需全部加入 Java classpath。

1. 解析包、游戏和加载器元数据，生成锁定清单，记录文件来源、完整性信息和目标位置。
2. 校验并入库缺失文件，准备完整的候选运行视图，再切换实例的当前版本。失败时保留原版本。
3. 用指定 Java 和解析出的主类、参数启动，以实例自己的游戏目录承载可写数据。可显式传路径的 classpath 文件可直接引用公共存储。加载器通过目录扫描发现的模组，需要在实例可见的 `mods/` 中落位。
4. 游戏退出后，释放运行引用。对象库清理只处理没有任何有效引用的对象，并先展示预计可释放空间。

## 共享文件如何落位

| 方式 | 使用条件 | 存储与兼容性 |
| --- | --- | --- |
| 直接引用公共路径 | 游戏或加载器允许显式传入路径，且通过启动验证 | 对象直接复用 |
| 硬链接 | 对象库和实例在同一支持硬链接的卷，且共享路径按不可变工件管理 | 运行期间仍共享数据块。原地写入会影响所有引用，文件只读属性只适合降低误写概率 |
| 临时复制 | 启动时有足够空间，且能追踪启动器创建的视图 | 运行期间占用副本空间，清理后恢复常驻去重收益 |

原生库解压目录按运行视图分配，避免在公共对象上解压或就地修改。对可写数据一律使用独立文件。

首版的落位选择以[运行时写入分类和诊断结果](runtime-files.md)为准。同卷硬链接仅用于已验证的托管只读文件。未知文件使用私有副本，运行期会修改的文件保留在实例目录。为同一实例换版本时只替换托管条目。

## 交付与验收

交付顺序见[开发路线](roadmap.md)。先在 Windows 上用 Rust 跑通本地离线原型，然后完成两种整合包格式、三种加载器和下载源验收，测量实际空间并验证维护操作，最后接入微软正版登录。

统计至少包含每个实例独立安装的基线、共享对象实际只计一次的占用、私有数据、临时副本及游玩峰值。Linux 写时复制文件系统或 Windows 文件系统虚拟化可在后续原型中比较。进程隔离和网络限制单独设计与验收。
