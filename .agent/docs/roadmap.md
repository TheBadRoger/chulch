# 开发路线

使用 Rust 实现 Windows CLI。第一阶段先跑通本地离线原型，再接入微软正版登录。离线原型以本地已备妥的合法游戏文件验收，下载以及账号接入随后按顺序交付。游戏运行使用用户指定的 Java，启动前检查版本和架构。

## 实现分工

首期使用一个 Cargo package，CLI 与核心以二进制入口和库模块划分。CLI 负责参数解析和呈现，核心按导入、下载、存储、加载器、运行视图和进程管理划分模块。使用版本化 JSON 保存实例配置和锁定清单，SHA-256 对象文件独立存放。共享状态由跨进程协调保护，实例当前版本引用在候选版本完整准备后提交。

数据流为 **导入或本地测试输入 → 安装计划 → 校验入库 → 锁定版本 → 生成运行视图 → 启动 Java**。三种加载器使用同一个存储和启动流程，适配器负责生成各自的安装步骤与启动参数。

## 里程碑

| 阶段 | 开发内容 | 完成条件 |
| --- | --- | --- |
| 1. 本地离线原型 | 建立 Rust CLI；从本地测试清单接入合法的 Minecraft、Java 和依赖；实现对象入库、游戏目录及 Fabric 启动计划 | 两个本地 Fabric 实例可各自进入单人世界、保存并重启；同内容输入只入库一份 |
| 2. 整合包安装 | 实现 Modrinth 与 CurseForge 导入、官方和镜像下载路由、Forge 与 NeoForge 安装适配、缺件补齐 | 两种格式均可完成安装，三种加载器均有实际启动用例；验证 BMCLAPI 命中、自定义镜像与校验失败回退 |
| 3. 存储验收与维护 | 记录运行写入、启用已验证的共享视图；实现更新、回退、完整性检查、清理预览和执行 | 对比独立安装与 mcdocker 的静置及游玩峰值；验证存档保留、提交中断恢复及跨实例引用保护 |
| 4. 微软正版登录 | 接入应用注册和所需的授权流程，验证 Java 版权益及玩家档案，接入登录、刷新和退出 | 使用真实正版账号完成登录与启动；过期、撤销、缺少权益均有清晰提示，凭证与包数据独立 |

第一阶段的本地清单是开发夹具。面向用户的安装入口从第二阶段起接受 `.mrpack` 和 CurseForge ZIP。加载器覆盖以实测的 Minecraft、Java 和加载器版本矩阵为准。

## 第一批可运行任务

1. 初始化 Cargo package，提供 `instance list` 和 `launch <id>` 的命令入口。
2. 写一份本地 Fabric 测试清单，固定 Minecraft、加载器和 Java 的版本，记录客户端、资源、库及模组的本地路径。
3. 实现流式 SHA-256 入库、版本化清单及两个实例的游戏目录。首次使用私有模组视图，保留后续切换落位方式的入口。
4. 生成并执行一份 Java 启动计划。记录游戏启动、退出码、存档和配置是否按实例落位，再对同内容对象执行去重检查。

运行阶段的硬链接取舍按[文件分类与实测方案](runtime-files.md)决定。微软正版登录阶段依赖可用的应用注册和授权条件，前序阶段可独立完成。
